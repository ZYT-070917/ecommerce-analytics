## [1.1.1] — 2026-11-25

> **修订版本（Z +1）**：主题配色补全到页面底色。
> 接口、数据、表结构无变化，只是把 1.1.0 里"换主题只换了主色"这件事补完。

### 修复 Fixed

#### 切换主题时页面底色不变

- **现象**：1.1.0 的主题只改主色（按钮、折线、KPI 数字），页面底色恒为冷灰 `#f4f6fb`、
  卡片恒为纯白。选"琥珀"只有线条变橙，整页仍是冷调，配色显得不搭。
- **根因**：主题表里只有 `accent` / `rgb` / 图表色板三组值，
  表面色（`--bg` / `--surface` / `--surface-sunk` / `--border`）全部写死在 `:root` 和
  `body.is-dark` 里，没有参与主题切换。
- **修复**：每套浅色主题补一组表面色，切换时由 JS 写入 `:root`；深色主题仍交回
  `body.is-dark` 处理，避免两处规则互相覆盖。

| 主题 | 页面底色 | 卡片 | 描边 |
|---|---|---|---|
| 靛蓝 | `#f1f4fb` | `#ffffff` | `#e3e9f3` |
| 青碧 | `#eaf5f2` | `#fcfffe` | `#d7eae5` |
| 罗兰 | `#f2effb` | `#fefcff` | `#e5dff4` |
| 琥珀 | `#fdf4e4` | `#fffdf9` | `#f1e2c9` |
| 绯红 | `#fdeff2` | `#fffcfd` | `#f5dde2` |

#### 底色只有纯色，缺少氛围

- 在底色之上叠加两团由主色派生、透明度约 10%（深色 18%）的径向渐变，
  分别落在左上与右上，换主题时整页的光感方向一致。
- 顶栏用同一处光源的极淡渐变过渡到卡片色，不再是一块突兀的纯白条。
- 渐变用 `background-attachment: fixed`，翻页时底色不动，避免整块背景跟着滑动。

### 变更 Changed

- 图表调色板 `P()` 的 `border`（环形图扇区间隙色）改为跟随主题卡片色，
  `split`（坐标分割线）跟随主题描边色 —— 切主题后 canvas 与 CSS 不会有色差。
- 新增 `<meta name="theme-color">`，切换主题时同步更新，移动端状态栏/地址栏跟随配色。
- 图表坐标轴文字色从 `#8896a8` 微调到 `#7e8ca1`，在五套暖/冷底色上对比度都够。

### 影响面 Impact

| 项目 | 影响 |
|---|---|
| API / 数据 / 表结构 | 无变化 |
| 前端文件 | `app.css`（body 背景、顶栏渐变、`--wash` 变量）、`app.js`（主题表加表面色）、`index.html`（meta） |
| ETL | 不需要重跑 |
| 兼容性 | 渐变与 CSS 变量均为长期支持的写法，老内核正常降级为纯色底 |

## [1.1.0] — 2026-11-25

> **次版本（Y +1）**：前端重构为五页横向翻板并加入主题配色。
> **接口、数据、表结构均未变化**，后端一行没动。

### 新增 Added

#### 五页翻板导航

- 按分析主题拆成五页：经营概览 / 客户价值 / 运营节律 / 商品结构 / 市场与单品。
- 四种翻页方式：滚轮、方向键（↑↓←→ / PgUp/PgDn / Home/End）、右侧页码轨、触屏左右滑动。
- 翻页用 `transform: translate3d` + `cubic-bezier(.22,.85,.24,1)`，配合每页元素的
  错峰淡入（`--i` 控制 52ms 级联延迟），进出都有层次。
- 支持深链：`#3` 直接落到第三页，翻页时地址栏同步更新。

#### 主题配色

- 6 套配色：靛蓝 / 青碧 / 罗兰 / 琥珀 / 绯红 / 墨夜（深色）。
- 切换时只改 CSS 变量并重绘图表，不发任何请求；选择记在 `localStorage`。
- `?theme=ink` 可直接指定配色，方便分享带主题的链接。

#### 新增两块内容（都复用已有接口）

- **月度订单量与客群规模**：第 3 页右图，`/api/trend` 的 orders / customers 字段。
- **GMV Top 10 单品**：第 5 页右图，`/api/top-products` 此前只用来查商品名。

#### 每页一句洞察

标题栏带 `Eyebrow` + 页标题 + 右侧口径说明；每张图配一句话结论，
数字用主题色加粗，直接从数据算出，不写死。

### 变更 Changed

#### 一次性预载，彻底去掉加载态

- 启动时把 8 个接口全部取完，再一次性渲染五个页面。
- 之后翻页、切主题都是纯前端操作，**不可能出现"加载中"**。
- 原来的骨架屏（`.sk`）、"载入中…"、"正在加载数据…" 全部移除。
- 启动遮罩延迟 200ms 才显形：后端有缓存时数据秒回，用户根本看不到遮罩。

#### 代码按职责拆成三个文件

| 文件 | 职责 | 行数 |
|---|---|---|
| `web/index.html` | 只放结构，五个 page 段落 | 318 |
| `web/assets/app.css` | 设计 token、布局、翻页、主题 | 775 |
| `web/assets/app.js` | 数据预载、图表、表格、翻页、主题 | 1,022 |

### 修复 Fixed（重构过程中暴露的真实缺陷）

1. **宽表格把整页撑出视口**
   - 现象：ABC 明细表把页面顶宽，右列被切到屏幕外，页码轨标签也错位。
   - 根因：flex 子项的 `min-width` 默认是 `auto`（等于内容最小宽度），
     `.page` 设了 `flex: 0 0 100%` 也压不住表格的最小宽度。
   - 修复：给 `.page` / `.card` / `.table-wrap` 统一加 `min-width: 0`。

2. **切换主题后顶栏不跟着变**
   - 根因：`background: color-mix(...)` + `backdrop-filter: blur()` 在部分内核里
     不重绘模糊层，顶栏停留在上一个配色。
   - 修复：顶栏改成不透明 `var(--surface)`，顺带兼容不支持 `color-mix` 的老浏览器。

3. **翻页位移与页面宽度基准不一致**
   - 轨道宽度改为 `calc(100% * var(--n))`、页面宽 `calc(100% / var(--n))`，
     位移按同一个基准算，避免百分比各自解析导致错位。

### 影响面 Impact

| 项目 | 影响 |
|---|---|
| API / 数据 / 表结构 | 无变化 |
| 前端文件 | `index.html` 重写；新增 `assets/app.css`、`assets/app.js`（从原单文件拆出） |
| ECharts | 已本地化到 `assets/echarts.min.js`，不再依赖 CDN |
| 兼容性 | 移除骨架屏与卡片级重试按钮，改为启动阶段的统一错误页 |

## [1.0.4] — 2026-11-25

> **修订版本（Z +1）**：新增一键启动入口，纯开发体验改进。
> 接口、表结构、数据均无变化，原来的手动两步方式仍然可用。

### 新增 Added

#### 一键启动 `run.py`

- **背景**：原来要两条命令（先 `python etl/build_dw.py` 建仓，再 `uvicorn api.main:app` 起服务），
  还要自己记端口、手动开浏览器。隔几天再来，很容易忘记先后顺序，也容易在库已建好的情况下
  白白重跑一次 5 分钟的 ETL。
- **实现**：`run.py` 串起三件事
  1. 查 `fact_sales` 行数 —— 表不存在或为 0 时才跑 ETL，已有数据直接跳过
  2. 启动 uvicorn
  3. 延迟 1.5 秒自动打开浏览器（等服务器真正监听后再开，否则会先看到"无法访问"）
- **参数**：`--rebuild` 强制重建、`--port` 换端口、`--no-browser` 不开浏览器
- **细节**：端口被占用时明确提示并退出（附带换个端口的建议），不会静默失败；
  `.env` 缺失时提示先复制模板，而不是抛一个连接错误堆栈。

#### Windows 双击启动 `start.bat`

- 自动调用 `.venv` 里的 Python，不需要手动激活虚拟环境。
- 该文件刻意保持**纯 ASCII + CRLF 行尾**。实测：用 UTF-8 内容 + LF 行尾写 bat，
  cmd.exe 会把多行 `if (...)` 块解析错乱，报 `'python.exe" (' 不是内部或外部命令`。
  中文提示统一交给 Python 打印（Python 自己处理编码）。
- 缺少虚拟环境时给出两条安装命令，而不是窗口一闪而过。

### 变更 Changed

- README「快速开始」改为一条命令 `python run.py`；
  原来的分步命令保留在下方，作为"想看清每一步在做什么"的等价方案。
- 环境要求由 Python 3.9+ 上调为 **3.11+**。原先写低了：pandas 3.x 的最低要求就是 3.11，
  `run.py` 也用了 `int | None` 这类 3.10+ 语法。

### 影响面 Impact

| 项目 | 影响 |
|---|---|
| API 接口 / 表结构 / 数据 | 无变化 |
| 新增文件 | `run.py`、`start.bat` |
| 兼容性 | 手动两步方式仍可用；`--reload` 热重载只保留在手动方式下 |

## [1.0.3] — 2026-11-25

> **修订版本（Z +1）**：性能优化与代码去重。**API 接口签名、表结构均未变更**，
> 指标数值零漂移（已逐项核对）。新增 2 个视图和 1 个组合索引，
> 数据库里已直接生效；若重跑 ETL，`schema.sql` 会自动重建它们。

### 优化 Changed

#### 1. 加结果缓存，页面二次加载从 69 秒降到 0.1 毫秒

- **背景**：看板一次加载会并发请求 8 个接口，每个接口都要对 104 万行做聚合。
  实测首次加载合计 **69.2 秒**，每次刷新都重算一遍，数据却没变。
- **实现**：`q()` 外面加一层进程内 TTL 缓存（默认 300 秒），key 为 SQL 加参数。
- **关键细节**：缓存命中时返回**副本**。原本 `weekday()` 会原地修改返回的
  `weekday` 字段（数字转中文），一旦命中缓存就会把缓存里的数据改掉，
  第二次请求拿到的便是被污染的副本。已改成返回新对象。
- **实测**：首次 69.2 秒 → 二次加载 **0.1 毫秒**。

#### 2. 8 段 SQL 的过滤条件收敛到两个视图

- **背景**：`WHERE is_return = 0` 在 `api/main.py` 里重复出现 8 次，
  其中 2 处还要再加 `AND is_product = 1`。口径一旦调整，得改 8 个地方，很容易漏。
- **实现**：`schema.sql` 新增 `v_sales`（正向销售）与 `v_product_sales`
  （正向销售 + 真实商品），8 段 SQL 全部改为查视图，过滤条件不再出现在应用层。
- **验证**：`EXPLAIN` 显示条件被下推到基表，走 `idx_fact_scope` 索引。

> 顺带说明一处**有意保留**的不一致：`/api/kpi` 的"活跃客户数"仍用
> `(SELECT COUNT(DISTINCT customer_id) FROM fact_sales)` 而没走 `v_sales`。
> 因为两边差 61 人（只有退货单、没有正向购买的客户），改口径会让 KPI 从 5,939 变成 5,878。
> 这属于指标定义变更，不该混在重构里，所以显式保留原值并加了注释。

#### 3. ABC 与 Pareto 的重复 CTE 合并

- 两个接口原本各写一遍「按 SKU 汇总 GMV、按金额降序累计」，连 CTE 名字都相同。
- 抽成模块级常量 `STOCK_GMV_CTE`，并利用 MySQL 8 支持窗口函数套聚合的特性
  （`SUM(SUM(amount)) OVER (...)`），把原来的两层 CTE 压成一层，净减 20 行。

#### 4. 新增组合索引 `(is_return, is_product, date_key)`

- 看板的查询几乎都同时带这三个条件，原来只有 4 个单列索引，用不上组合。
- 实测 `EXPLAIN` 已从走 `idx_fact_date` 改为走 `idx_fact_scope`。

#### 5. 锁定依赖版本

- `requirements.txt` 从 9 个 `>=` 改为 `==` 精确锁定（当前环境实测通过的组合）。
- 动因：只写 `>=` 时实际装到了 **pandas 3.1.1**（相对 2.x 有破坏性变更，
  例如默认字符串类型改变），换台机器可能装到 2.x 而得到不一致的结果。

#### 6. 文档描述与代码核对

- 核对 README 与 CHANGELOG 中关于接口数量、并发请求数、测试脚本的描述，
  已与实际代码一致（此前提到过的 `verify_*.py` 并不存在，已改为如实说明"无测试用例"）。

### 已知问题（本次新增）

#### 首次加载仍然慢，瓶颈是 MySQL 缓冲池配置，不是代码

- `innodb_buffer_pool_size` 为默认的 **128 MB**，而 `fact_sales` 含索引约 **239 MB**，
  整表装不进内存，每次聚合都要重新读盘。
- 实测分解：`COUNT(*)` 0.21 秒（走索引），`GROUP BY country` 5.35 秒（全表扫），
  `COUNT(DISTINCT invoice_no)` 5.08 秒（建临时表），`COUNT(DISTINCT customer_id)` 0.67 秒
  （有单列索引，走松散索引扫描）。
- 缓存只解决"第二次之后"，**首次打开看板仍需等十几秒**。
- 可选方案：把缓冲池调到 512 MB~1 GB（改 `my.ini` 后重启 MySQL，零代码改动），
  或建预聚合汇总表（改动大，非必要）。

### 升级步骤 Upgrade

```bash
pip install -r requirements.txt     # 依赖版本锁定，建议在干净环境重装
uvicorn api.main:app --reload --port 8000
```

数据库侧已直接执行了 `ALTER TABLE ... ADD KEY` 与 `CREATE VIEW`；
若重跑 ETL，`schema.sql` 会自动重建索引和视图，无需手工干预。

| 项目 | 影响 |
|---|---|
| API 接口 | 无变化（返回字段、数值与 1.0.2 完全一致） |
| 表结构 | 无变化（仅新增 1 个索引、2 个视图） |
| 性能 | 二次加载 69 秒 → 0.1 毫秒；首次加载不变 |
| 依赖 | 需按 `requirements.txt` 精确版本安装 |

## [1.0.2] — 2026-11-25

> **修订版本（Z +1）**：修正维度表口径、补齐数据血缘、收敛硬编码。
> ⚠️ **表结构有变更**（`fact_sales` 新增 3 列、`dim_customer` 删除 1 列），升级必须重跑 ETL。

### 修复 Fixed

#### 1. `dim_customer` 的订单数与金额口径和 RFM 对不上账

- **根因**：`dim_customer.total_orders / total_amount` 按全表聚合，把邮费、非商品项
  和退货负值都算了进去；而 `/api/rfm` 的 F / M 只统计 `is_return=0`。
  同一个客户在两张表里会有两个不同的消费额，无法互相校验。
- **修复**：拆成两块聚合 —— 首末单日期与国家级看客户全生命周期（含退货），
  `total_orders / total_amount` 只算正向销售，与 RFM 完全同源。
- **验证**：客户 17850 在 `dim_customer` 与 RFM 口径下均为 **51,208.87**，一致。

#### 2. 商品描述取 `last`，会被促销短名覆盖

- **根因**：`dim_product` 用 `agg(description=("description", "last"))`，
  同一 SKU 若最后一次录入的是促销短名甚至空描述，完整品名就被覆盖。
- **修复**：新增 `longest_description()`，跳过 `(无描述)` 后取最长的一条。
- **结果**：`dim_product` 中 `(无描述)` 的商品数降为 **0**。

#### 3. `dim_customer.is_guest` 恒为 0 的死字段

- **根因**：该表只装有 `customer_id` 的客户，游客根本不进来，所以这列永远是 0；
  而 `clean()` 里算出的 `is_guest` 反而没写进事实表。
- **修复**：标记位跟着事实走 —— `is_guest` 移入 `fact_sales`，`dim_customer` 删掉该列。
  现在可以直接 `WHERE is_guest = 1` 统计游客，不用再写 `customer_id IS NULL`。

#### 4. `line_no` 与 Excel 源行号脱钩，出问题无法回溯

- **根因**：`line_no` 是清洗删行后按订单重新编号的，和源文件行号没有对应关系，
  发现一条脏数据时无法定位到原始 Excel 的哪一行。
- **修复**：`extract()` 阶段打上数据血缘 ——
  `source_sheet`（来自哪个 sheet）+ `source_row`（在源 sheet 中的行号，表头占第 1 行）。

### 优化 Changed

- **字段长度不再两处维护**：`build_dw.py` 顶部新增 `LEN_INVOICE / LEN_STOCK / LEN_DESC`
  等常量，与 `schema.sql` 的 VARCHAR 声明一一对应，改一处即可。
- **库名不再硬编码**：库名由 `DATABASE_URL` 解析（`DB_NAME`），
  `schema.sql` 移除了 `CREATE DATABASE` 与 `USE`，改为纯 DDL，
  库名从原来的 3 处收敛到 `.env` 1 处。
- **数据周期不再写死**：`/api/kpi` 新增 `date_from` / `date_to`，
  前端状态栏由接口返回值拼接，换数据集不用改前端。
- **补齐 CORS 与全局异常兜底**：新增 `CORSMiddleware`（本地开发放开，公网部署需收紧）；
  数据库连不上时返回结构化的 JSON 错误并记录堆栈，前端不再只看到裸 500。

### 修复 Fixed

#### 1. 两个 sheet 日期重叠导致重复计数（数据准确性）

- **现象**：月度趋势里 2010-12 出现反常尖峰 —— GMV £1,262,598 但只有 1,559 个订单，
  客单价 £810，而邻月为 £535。
- **根因**：Online Retail II 第一个 sheet 覆盖到 2010-12-09，第二个从 2010-12-01 开始，
  两段有 **9 天重叠**。`extract()` 直接 `pd.concat(sheets.values())`，这 9 天被读两遍。
- **证据**：22,345 行重复明细，归为 22,025 组，两次出现的 `sales_id` 间隔全部落在 20,000 至 25,000
  之间，即第一个 sheet 尾部与第二个 sheet 头部，且重复行全部集中在 2010-12-01 至 09。
- **修复**：改动位置为 `etl/build_dw.py` 中的 `extract()`，第二个及以后的 sheet 只保留
  第一个 sheet 最后一天之后的行。没有使用整体 `drop_duplicates`，
  因为同一订单里同商品买两次属于合法业务数据，这类合法重复仍有 11,806 行，必须保留。
- **结果**：行数由 1,061,164 降为 1,038,819；GMV 由 £20,972,595 降为 £20,533,742，降幅 2.09%；
  2010-12 回落到 £823,746，客单价 £528，与邻月一致。

#### 2. 金额币种纠正，由 ¥ 改为 £

- 数据源是英国在线零售商，`Price` 单位为**英镑**。此前看板 `money()` 与 README
  统一按 `¥` 渲染，属于单位错配。
- **修复**：`web/index.html` 的 `money()` 改为 `£`，README 中 25 处金额同步更新。

#### 3. 退货率不再假设退货数量为负

- **根因**：`/api/kpi` 用 `-SUM(退货金额) / SUM(正向金额)`，隐含假设退货行 `quantity` 均为负数。
  一旦数据里出现正数量的退货单，退货率会被算成负值。
- **修复**：改为 `ABS(SUM(退货金额)) / SUM(正向金额)`，对符号不敏感。
- **结果**：退货率由 7.28% 降为 7.14%。

### 修复 Fixed

按发生顺序记录，均已在当前代码中修正：

1. **`nan can not be used with MySQL`**（装载中断）
   - 根因：pymysql 无法序列化 pandas 的 `float('nan')`
   - 修复：新增 `to_nullable_int()` 工具函数，`astype(object).where(notna(), None)` 把 NaN 转成真正的 `NULL`

2. **`Duplicate entry '15056bl' for key 'dim_product.PRIMARY'`**（装载中断）
   - 根因：同一 SKU 存在 `15056BL` / `15056bl` 两种写法；MySQL `utf8mb4_unicode_ci` 不区分大小写，
     两个变体被当作同一个主键，引发冲突
   - 修复：`clean()` 中对 `stock_code` 做 `.str.strip().str.upper()` 统一

3. **帕累托图与商品榜被邮费污染**
   - 现象：`POST`（邮费）、`M`（手工调整）、`GIFT_0001_xx`（礼品券）排进商品 Top 榜
   - 根因：这些虚拟编码金额不小，但混入商品维度分析会让 ABC 分类和帕累托曲线失真
   - 修复：新增 `is_product` 标记（12 个固定编码 + `GIFT_0001` 前缀），
     所有商品维度查询加 `AND f.is_product = 1`；维度表 `dim_product` 只收真实商品

4. **`(1064, ... You have an error ... near 'lines')`**
   - 根因：`lines` 是 MySQL 8 保留字，作为列别名触发语法错误
   - 修复：别名改为 `line_count`，API 返回字段与前端 `k-lines` 读取逻辑同步修改

5. **`(1049, "Unknown database 'biz_analytics'")`**（首次运行/删库后必现）
   - 根因：`load()` 用带库名的 `DB_URL` 建立连接，但库不存在时连接直接失败；
     而 `CREATE DATABASE` 写在 `schema.sql` 里，需要先连上库才能执行，形成死循环
   - 修复：`load()` 开头新增三步，先用不带库名的 `SERVER_URL` 连到服务器，执行
     `CREATE DATABASE IF NOT EXISTS`，再 dispose 该连接，之后切换到 `DB_URL` 建表装载
   - 效果：用户手删数据库后仍可一键重跑，无需手动建库

6. **月度趋势月份排序错乱**
   - 现象：`2010-10` 排在 `2010-02` 前面
   - 根因：`month_name` 是 `'2009-12'` 形式的字符串，`ORDER BY` 走字典序
   - 修复：改为 `ORDER BY MIN(date_key)`，用数字日期键排序

7. **`BadZipFile: File is not a zip file`**（Windows 环境）
   - 根因：`raw/online_retail_II.xlsx` 是软链接而非真实文件，`openpyxl` 读取失败
   - 修复：改用真实文件复制，不使用符号链接
   - 说明：此项为环境问题，非代码缺陷，但已记录进 README 常见问题一节

### 优化 Changed

- `country` 字段缺失值处理：从 `astype(str)`（会把缺失变成字符串 `"nan"`）改为
  `astype(object).where(notna(), None)`，正确写入 `NULL`
- `quantity` / `price` / `amount` 列在装载前统一 `round(2)` 并按目标字段类型对齐
  （`stock_code` 截断为 VARCHAR(32)，`invoice_no` 截断为 VARCHAR(20)）
- 维度表装载 `chunksize` 设为 5000，事实表 10000
- 日期维度用 `pd.date_range` 生成连续日期序列，保证无订单日也有行（趋势图不断点）
- 客户维度 `total_orders` 使用 `nunique` 而非 `count`，避免"订单内多行"被重复计数

### 已知问题 Known Issues

> 以下为**当前版本（1.0.4）**仍存在的问题，随修复逐条移出。

- **全量重建耗时长**：每次运行都要重装 104 万行（约 5 分钟），数据量再涨需要改增量方案
- **无鉴权**：API 无任何认证，仅适合本地运行，不能直接公网暴露
- **无分页**：`/api/top-products`、`/api/country` 用 `LIMIT` 参数控制，但没有分页游标
- **RFM 季节性偏差**：`recency` 以数据最后一天（2011-12-09）为基准，
  若数据窗口末端有淡季，会系统性地让更多客户被判为"流失"
- **游客订单未纳入客户分析**：**229,328 行**（3,499 个订单，GMV 约 **£310.2 万**，占总 GMV 的 15.1%）
  无 `customer_id`，计入 GMV 但不参与 RFM，
  因此"客户数 × 客单价"与总 GMV 不构成严格的等式关系
- **仅支持全量刷新**：无增量/调度机制，需手动重跑 ETL
